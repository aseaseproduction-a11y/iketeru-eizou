# 較正テスト実施プロトコル（事前固定版・v5）

本プロトコルは、較正テストの実行前にすべての条件・データ分割・隔離環境・実行ごとランダム不透明ID（`blind_id`）と固定パス文法・凍結ひな型による指示文完全一致監査・ファイル別メディア確認・解像度非対称の記録・`scdet`/スロー区間パラメータ・調整回数上限・方式採用ルール・合格基準を固定し、結果を見た後の基準変更（後出し調整）を禁止するために策定する。

---

## 1. テストの位置づけ（試しの較正・本番DB非書込）
- 本テストは **「試しの較正（Dry-run）」** として実行し、**本番TiDB / SQLite への書き込みは一切行わない**。
- 結果は採点方式（静止画方式 vs 動画方式）の精度比較および改善目安として扱い、そのまま本番ランクの付け直しには使用しない。

---

## 2. 動画読み込みの技術的前提（1fpsの限界）・無圧縮供給・共通実測値・スロー区間パラメータ固定
1. **1秒1コマ（約1fps）の限界および解像度の非対称性の明記**：
   - Antigravity の `read_file` でローカル `.mp4` を読み込む際、映像は**およそ1fps（1秒1フレーム）**で抽出・供給される（音声トラックは連続波形として全編聴取可能）。
   - さらに、`8pOOxOo7YYo`（755.76秒）の実測入力トークン数は **`79,678` トークン（約 105 トークン/秒）** であり、Gemini の低解像度動画フレーム設定（1コマ約66トークン＋音声約32トークン/秒）と同程度とみられる。
   - したがって、動画方式のフレームは低解像度である可能性が高く、**静止画方式のコンタクトシート画像とは細部（小文字テロップ、微細なテクスチャ、細部のコンポジット品質等）の見え方が異なる（解像度の非対称性がある）**こと、および1秒未満の高速カット・細かい動きは見落とす限界があることを前提条件として必ずレポートに明記する（「動画方式＝動きを完全に把握できる」とは絶対に表記しない）。
   - **入力トークン数の記録義務**：静止画方式・動画方式とも、すべての採点実行で `transcript.jsonl` から **`first_post_read_input_tokens` / `max_input_tokens` / `total_input_tokens` / `total_output_tokens`** を自動抽出してログおよびレポートに記録する。
2. **再圧縮なし（取得元画質・音質のまま公平供給・実測検証済み）**：
   - 全82本中で最大・最長の `8pOOxOo7YYo`（`42,094,264 bytes = 40.14 MiB`、`755.76秒`、`640×360`）を独立サブエージェント（`1b7e8541-d6d5-4dea-a5b7-56bf3c65a7ee`）で `read_file` 実測した結果、**無圧縮のまま正常読み込み・冒頭／中盤／末尾の映像および音声の全編確認（`video/mp4`・`input_tokens: 79,678`）に成功した**（`analysis/video_size_limit_check.json`）。
   - したがって、15MB超を一律再圧縮するルールは撤廃し、**全82本を取得元の画質・音質のまま再圧縮せずに供給**する（一部作品だけ画質・音質を下げる不公平を排除する）。
   - 例外的に本番実行中にサイズ／トークン上限エラーが発生した場合のみ、エラー内容と実測上限を記録し、該当動画の扱いを第5章の失敗時ルールに従って処理する。
3. **両方式への共通実測値提供（`ffmpeg scdet` しきい値・LUFS 固定）**：
   - 静止画方式・動画方式の**双方に同一フォーマットで `ffmpeg scdet` 実測値と音声ラウドネス（`ebur128` 統合ラウドネス LUFS）を添えて**渡す。
   - **`ffmpeg scdet` パラメータ（固定）**：`scdet=threshold=10:sc_pass=0`（0〜100スケールで `lavfi.scd.score >= 10.0` をカット点として検出）。
   - **提供数値**：総尺（秒）、総カット数、平均カット間隔（秒）、10秒窓の最大カット数（`max_cuts_per_10s`）、統合ラウドネス（LUFS）。
4. **高密度区間スロー確認ルール（パラメータ完全固定・恣意選択禁止）**：
   - 細かい動き・高速カットが採点に影響する区間を実質 2〜4fps で確認するため、以下の**100%決定的な機械ルール**でスロー区間を自動抽出する（人間やAIが結果を見て区間を恣意的に選ばない）：
     - **スライディング窓の刻み幅（固定）**：**1.0秒刻み**（開始時刻 `t = 0, 1, 2, ..., max(0, floor(duration) - W)`。動画長 `< W` の場合は単一区間 `[0, duration]`）。
     - **同点時の選び方（固定）**：同じ最大カット数を持つ窓が複数ある場合は、**最も早い区間（開始時刻 `t` が最小の区間）** を選択する。
     - **適用条件・倍率・窓幅（固定）**：
       1. `max_cuts_per_10s >= 12`（超高速カット・平均0.83秒未満）：窓幅 `W = 5秒`・1.0秒刻みで全編から最大カット数の5秒区間（同点時は最も早い区間）を切り出し、**4倍スロー（`setpts=4.0*PTS`、出力20秒・実質約4fps、無音 `-an`）**を生成。
       2. `6 <= max_cuts_per_10s < 12`：窓幅 `W = 10秒`・1.0秒刻みで全編から最大カット数の10秒区間（同点時は最も早い区間）を切り出し、**2倍スロー（`setpts=2.0*PTS`、出力20秒・実質約2fps、無音 `-an`）**を生成。
       3. `max_cuts_per_10s < 6` かつジャンルが `モーション`：中央10秒区間（`start = max(0, floor((duration - 10) / 2))`, `end = min(duration, start + 10)`）を切り出し、**2倍スロー（`setpts=2.0*PTS`、出力20秒・実質約2fps、無音 `-an`）**を生成。
     - **静止画方式との公平比較**：
       - スロー区間が発動した同一動画・同一区間 `[start, end]` について、静止画方式でも**同じ密集区間を切り出した高密度4×4コンタクトシート（16フレーム追加）**を供給し、時間分解能の偏りを防ぐ。
     - **記録義務**：全動画について `scdet_threshold`, `max_cuts_per_10s`, `slowmo_applied`, `slowmo_factor` (`2x`/`4x`), `slowmo_window_sec` (`[start, end]`) をログに記録する。

## 3. 厳格な隔離環境・ブラインド化・機械監査ルール
1. **採点者の完全分離（新規サブエージェント限定）**：
   - 採点は1動画・1実行ごとに**必ず新しい独立サブエージェント**が行う。
   - 親エージェント（事前確認で `5URefVYaJrA` / `tdQCMuaJUQk` / `7rP-633ApUI` を視聴済み）は**一切採点しない**。
2. **完全独立の隔離フォルダ・実行ごとランダムID（`blind_id`）・機械的固定パス文法（必須）**：
   - 採点対象ファイルの配置先は、リポジトリ（`E:\iketeru-eizou`）とも親エージェントの `brain\` フォルダとも完全に無関係な新規トップレベルフォルダ **`E:\iketeru_blind_eval\<run_id>\<mode>\<blind_id>\`** に固定する（`D:\` は Google Drive 仮想ドライブで直下ディレクトリ作成不可のため、ローカル NTFS の `E:\` 直下に独立作成）。
   - **有名作品の YouTube/Vimeo ID 記憶リスクを断つため、元の動画IDはパス・ファイル名・採点指示文のいずれにも一切使用しない**。実行（`run_id`）ごとにランダム生成する **12桁小文字英数字の不透明ID（`blind_id`: `^[a-f0-9]{12}$`）** を `scripts/lib/blind-id-map.mjs` で割り当て、元の動画IDとの1対1対応表（`blind_id_map.json`）は必ず隔離フォルダの外（リポジトリ側の `analysis/runs/<run_id>/blind_id_map.json`）に保管する。
   - **パスおよびファイル名は自由文字列を一切禁止**し、以下の機械的固定文法のみを許可する：
     - `run_id`：`^run_\d{8}_\d{6}$`（例：`run_20261122_190000`）
     - 動画方式：`E:\iketeru_blind_eval\<run_id>\video\<blind_id>\<blind_id>.mp4`（スロー発動時は `<blind_id>_slow.mp4` を併置）
     - 静止画方式：`E:\iketeru_blind_eval\<run_id>\contact_sheet\<blind_id>\<blind_id>_sheet_01.jpg` 等（`\d{2}` 連番、高密度区間発動時は `<blind_id>_sheet_dense.jpg` を併置）
   - `E:\iketeru_blind_eval\<run_id>\` 配下には上記採点対象ファイル以外を一切置かない（`blind_id_map.json` の隔離フォルダ内保存もコード上で禁止）。
   - 採点プロンプトには **元の動画ID・作品タイトル・チャンネル名・動画URL・既存DBランク・受賞歴・AI分析本文を一切渡さない**（渡すのは上記固定文法の隔離ファイルパスと共通の `ffmpeg scdet`/LUFS 実測数値のみ）。
3. **採点後の会話ログ機械監査（対応表照合＋凍結ひな型完全一致＋ファイル別メディア検証・違反は即無効）**：
   - 採点指示文は必ず **`scripts/lib/calibration-prompt-template.mjs` の凍結ひな型** から生成し、差し込める値は**「`run_id`・`blind_id` から機械的に決まる隔離ファイルパス」と「`ffmpeg scdet` / LUFS / スロー区間の数値のみ」**に厳格限定する（自由な `run_id`・自由なファイル名・元動画ID・`..`・自由文字列の差し込みを構造的に禁止）。
   - 採点完了後、全サブエージェントの `transcript.jsonl`（`truncated_fields` がある場合は `transcript_full.jsonl`）に対して **`scripts/audit-blind-transcript.mjs --strict --parent-id <親会話ID> --prompt-spec <spec.json> --blind-map <blind_id_map.json>`** を実行し、以下をすべて機械検証する（`--strict` では `--parent-id`・`--prompt-spec`・`--blind-map` の3つを必須とし、いずれか省略時は自動で `valid: false`・終了コード1とする）：
     - **(a) 対応表による `video_id` ↔ `blind_id` ↔ パス一致検証**：隔離フォルダ外の `blind_id_map.json` を用いて、監査対象の `video_id` に対応する一意の `blind_id` を照合し、指示仕様・フォルダ名・ファイル名接頭辞がすべてその `blind_id` と完全一致すること（別作品のフォルダや元の動画IDが混入した場合は即無効）。
     - **(b) 凍結ひな型との完全一致照合（根本対策）＋多層漏洩検査**：`USER_INPUT` / `SYSTEM_MESSAGE` から抽出した指示文が、`--prompt-spec` から再生成した凍結ひな型文字列と**1文字の差異もなく完全一致**すること。加えて多層防御として、元の動画ID・作品固有のタイトル・URL・賞名・部門名・チャンネル名および単独ランク表記・広範な賞キーワードの混入チェックも併用する。
     - **(c) 許可ツールの厳格ホワイトリスト**：サブエージェントのツール呼び出しは、以下の**2種類のみ**を許可する：
       1. 割り当てられた隔離フォルダ内の対象ファイルパスに対する **`read_file`**
       2. 指定された親エージェントの会話ID（`--parent-id`）へ結果を返す **`send_message`**
       これら以外のツール呼び出し（`run_command` / `search_web` / `list_dir` / 割り当て外ファイル・別動画フォルダ・自由ファイル名・元動画IDパス・`..` パスへの `read_file` / 親以外への `send_message` 等）が1回でもあれば**自動無効**とする。
     - **(d) 割り当てファイルごとの直後メディア確認**：`read_file` の各呼び出しの**直後のレスポンスステップ**に、ファイル種別に対応する実メディア（`.mp4` なら `video/mp4`、`.jpg`/`.png` なら `image/*`）が存在することを**割り当てた全ファイルそれぞれについて**確認する。
     - **(e) 自動回帰テストの維持**：上記 (a)〜(d) を偽ログで検証する自動テスト（`scripts/audit-blind-transcript.test.mjs`）を `node --test` で常時パスさせる。
4. **採点後の既知・表示チェック（感度分析）**：
   - 点数確定後（同じ応答の末尾）に、採点者へ以下の3問を必ず回答させる：
     1. `knows_work`：この作品（ブランド・アーティスト・作品名）を知っていたか
     2. `knows_award_history`：この作品の公的な表彰・選出歴を知っていたか
     3. `award_badge_visible_in_video`：動画の画面内や音声内に表彰・選出マークやトロフィー等が表示されていたか
   - 集計レポートでは、**①全件を含む結果**と、**②上記いずれかに該当した作品を除外した結果**の両方を必ず併記する。

## 4. 調整回数上限・合格基準・方式採用ルール・Holdout 1回限り凍結
1. **調整用（Dev）での調整回数上限（両方式で同一固定）**：
   - 静止画方式・動画方式ともに、調整用（Dev）でのプロンプト・ルーブリック調整は **最大3イテレーション（`v1_baseline` → `v2_tuned` → `v3_final`）** を上限とし、両方式に同一の調整予算を適用する。
2. **確認用（Holdout）の固定合格基準（結果を見て変更しない）**：
   - 合否は **確認用セット（Holdout）の点推定値** で判定し、**ブートストラップ95%信頼区間（$B=2,000$回）を必ず併記**する。

| 指標 | 対象 | 合格基準（固定・点推定値） | 算出仕様 |
|---|---|---|---|
| **順位相関（Spearman $\rho$）** | Holdout `craft_benchmark`（14本） | **$\rho \ge 0.85$** | 平均順位法（同点補正付き）＋95%信頼区間、Kendall's $\tau_b$ 併記 |
| **誤差（Band-distance MAE）** | Holdout `craft_benchmark`（14本） | **$\text{MAE} \le 4.0$点** | 正解ランク帯 $[L_i, U_i]$ 内なら `0`、帯域外なら最も近い端までの点差の平均 |
| **順位の正解率（Pairwise / ROC-AUC）** | Holdout `A-`以上 `craft_benchmark`（14本） vs Holdout `non_award_baseline`（20本） | **$\ge 0.85$** | 受賞・選出作のAI点数 ＞ 非受賞商用作品のAI点数となる組み合わせ割合＋95%信頼区間 |

3. **静止画方式 vs 動画方式の採用判断ルール（事前固定）**：
   - 確認用（Holdout）の点推定値に基づき、以下の決定表で機械的に判定する：
     - **ケースA（片方のみが3つの合格基準をすべて達成）**：合格した方式を採用候補とする。
     - **ケースB（両方とも3つの合格基準をすべて達成）**：確認用（Holdout）の3主要指標（`Spearman ρ` 高値優位、`Band-distance MAE` 低値優位、`Pairwise正解率` 高値優位）について、実質差の基準（`Δρ >= 0.02`、`ΔMAE >= 0.5点`、`ΔPairwise >= 0.02`）を超える勝ち数を比較する。
       - 勝ち数が多い方式（`3–0` / `2–0` / `2–1` / `1–0`）を採用候補とする。
       - 勝ち数が同数の場合（`1–1`）：`Band-distance MAE`（低値優位）→ `Spearman ρ`（高値優位）→ `Pairwise正解率`（高値優位）の優先順で採用候補を決定する。
       - 3指標すべてが実質差未満（`|Δρ| < 0.02` かつ `|ΔMAE| < 0.5` かつ `|ΔPairwise| < 0.02`）の場合：**「精度同等（実行時間・トークンコスト優位の方式を採用候補）」** と判定する。
     - **ケースC（両方とも1つ以上の合格基準を未達）**：**両方式とも不採用（本番適用不可・設計見直し必要）** とする。確認用の数値差は診断参考値としてのみ報告する。
4. **確認用（Holdout）の1回限り原則と完全凍結（Freeze Commit）**：
   - **確認用セットは両方式とも1回だけ実行する**。不合格だった場合、同じ確認用セットを使ってプロンプトを再調整・再判定してはならない。
   - 確認用を実行する直前に、**採点プロンプト・ルーブリック・使用モデル名・アンサンブル条件（2+1方式）・`scdet`/スロー適用スクリプトをすべて git コミットして凍結**し、確認用レポートにその **凍結コミットハッシュ（SHA）** を明記する。
